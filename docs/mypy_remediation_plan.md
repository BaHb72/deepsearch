# Mypy 告警治理方案

## 现状评估
- 最新一次执行 `uv run mypy deepsearch --hide-error-context --pretty` 的结果为 485 条类型告警，覆盖 80 个文件，较上一轮统计（518 条）已有回落。告警仍然集中在配置、数据提供商、基础设施以及 Web API 层，类型包括第三方库缺少类型桩、`Any` 逸出、异步上下文管理器误用以及老旧代码缺少注解等。
- 近期告警数量曾出现短暂上升，主要原因是我们为 `aiohttp`、`asyncpg`、`sqlalchemy` 等可选依赖补充了最小类型桩，使得 mypy 能够深入检查过去被视作 `Any` 的调用路径，真实问题由此暴露并计入统计。
- 由于 `mypy` 默认未启用 `--check-untyped-defs`，大量未标注函数暂未纳入静态检查范围，需要在后续阶段逐步收紧。

## 治理原则
1. **增量锁定**：优先针对新增或活跃模块引入类型约束，避免告警回潮；通过基线文件或模块白名单控制范围。
2. **分层推进**：按照“公共类型 → 基础设施 → 数据提供商 → Web/API/前端接口”的顺序逐步扩展治理深度，确保底层依赖先行稳定。
3. **自动化支撑**：将 mypy 校验整合进 CI，提供分类统计脚本，保证治理进展可量化。
4. **文档同步**：每个阶段完成后更新开发文档，沉淀约定及最佳实践。

## 阶段目标
### 阶段一：基线与工具化（当前进行）
- 建立告警分类清单，识别可通过补充类型桩或简单注解快速消除的错误。
- 为 mypy 引入 `--warn-return-any`、`--warn-unused-ignores` 等选项，并生成初始基线（如 `.mypy_baseline.json`），防止告警反弹。
- 修复配置模型与核心工具模块的高优先级告警，为后续模块提供示范。

### 阶段二：基础设施治理
- 重点清理 `deepsearch/config`、`deepsearch/infrastructure` 与 `deepsearch/core` 下的告警，补齐异步上下文管理器类型、数据库会话签名及缓存组件注解。
- 为常用第三方库（如 `asyncpg`、`sqlalchemy`、`redis`、`rich` 等）引入自定义类型桩或安装官方 stubs。

### 阶段三：业务与接口层治理
- 梳理数据提供商、回测、Web API 等业务模块的动态字段，补充数据模型与序列化逻辑的类型定义。
- 针对无法在短期内清理的第三方依赖，统一通过协议类或 `TypedDict` 抽象访问接口。

### 阶段四：提高准入门槛
- 在主要子模块启用 `--check-untyped-defs`，并通过门禁脚本保证新增代码默认带类型注解。
- 建立发布前检查清单，明确“无告警”作为合并条件之一。

## 度量与追踪
- 维护 `tools/typecheck/error_dashboard.py`（后续新增）脚本，按模块/错误类型输出统计。
- 在 CI 中记录告警数量曲线，确保每次合并后告警总数不增加。
- 每个阶段设定明确的目标数值（例如阶段一目标：配置模块零告警，整体减少 5% 以上）。

## 首批治理范围
- 以 `deepsearch/config` 模块为切入点，修复通知、日志等模型中的类型问题，确保配置加载路径在 mypy 下通过。
- 同步清理 `deepsearch/infrastructure/providers/datafeed/qmt/validator.py` 等关键验证逻辑中的 `Any` 返值与可空参数默认值问题，减少后续数据质量告警。
- 完成上述子模块后，再逐步扩展到缓存、数据库与 Web API 层，按模块提交，保持每次迭代可审查、可回滚。
