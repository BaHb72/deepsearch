# 数据源管理体验重构方案

## 背景与目标
- 现有界面存在“已启用但未测试”状态混淆、凭证读取失败、配置多处存储不一致等问题，影响运维效率。
- 本方案希望统一状态模型、规范配置读写路径、优化前后端交互流程，提升用户对启用链路的可理解性与可控性。

## 当前痛点复盘
- **状态语义不清晰**：初始化时所有数据源状态都被设为 `untested`，即便后台已启用也无法反映真实运行状况。
- **配置结构割裂**：后端读取 `data_sources.providers.*.config.connection`，示例配置仍写在旧的顶层 `amazingdata.*` 节点，导致前端加载时字段为空。
- **测试与启用耦合混乱**：启用开关会隐式触发测试且缺乏提示，失败后也不会重置开关，用户难以判断当前阶段。
- **反馈信息不足**：测试、启用异常只返回简单字符串，缺少可操作建议与日志查询入口。

## 状态模型重设计
| 状态 | 触发条件 | 用户含义 | 后续操作 |
| --- | --- | --- | --- |
| `draft` | 新建后未保存或配置不完整 | 尚未准备测试 | 完成必要字段并保存 |
| `pending_test` | 配置保存但尚未测试 | 待测试 | 点击“测试连接”或“启用”触发测试 |
| `testing` | 后端正在执行测试 | 进行中 | 等待结果，可取消 |
| `ready` | 最近一次测试成功但尚未启用 | 可启用 | 可立即启用或保持待命 |
| `active` | 已启用且最近心跳健康 | 正常运行 | 监控维持；可停用 |
| `degraded` | 启用后健康指标异常但可访问 | 有风险 | 查看诊断、重新测试 |
| `error` | 测试或运行失败 | 无法正常使用 | 修复配置再测 |
| `offline` | 手动停用 | 暂停服务 | 重新启用前需测试 |

- 后端保存配置时仅允许进入 `pending_test`，测试通过才能晋升 `ready`，启用成功后进入 `active`。
- 监控模块根据请求统计自动在 `active` ↔ `degraded` ↔ `error` 间切换，并记录 `last_health_check`。

## 后端改造要点
1. **配置统一与迁移**
   - 目标结构：`data_sources.providers.<type>.config.connection.*`、`local.*` 等层级。
   - 读取时兼容旧节点，发现旧格式即自动迁移写回新格式，并写入 `has_saved_credential` 标识。
   - 更新 `settings.*.yaml.example` 与模板文件，标注敏感字段占位符。
2. **API 行为调整**
   - `POST /api/data-sources/create`：校验必填字段，写入配置，状态强制 `pending_test`。
   - `PUT /api/data-sources/{id}/update`：默认保留旧凭证，除非请求体提供新值；保存后状态回落至 `pending_test`。
   - `POST /api/data-sources/test`：进入 `testing`，执行真实连通性，返回 `{success, status, message, details}`，记录测试日志。
   - `PATCH /api/data-sources/{id}/toggle`：
     - 若目标启用且当前非 `ready`/`active`，先调用快速测试；成功则切 `active`，失败保留 `pending_test`/`error`。
     - 禁用后状态设为 `offline`，中止后台连接。
   - 所有接口返回字段包含 `status`, `lastTestTime`, `testSummary`, `hasSavedCredential`。
3. **监控回写**
   - 观测到连续失败时自动降级状态，写入 `degraded_reason`。
   - 对成功率、延迟位置保留历史，供前端展示。
4. **日志与可追踪性**
   - 为测试、启用流程写入结构化日志，附带 `datasource_id`、`stage`、`duration`，支持后续聚合。

## 前端交互设计
1. **列表视图**
   - 列表标签根据状态显示颜色与提示语；`pending_test` 显示“待测试”，`ready` 展示“可启用”。
   - 操作按钮：`测试连接`、`启用/停用`、`编辑`、`诊断`、`查看日志`，根据状态动态启用。
   - 提供顶部告警条，提示所有 `pending_test` 数据源数量和快速测试入口。
2. **表单体验**
   - `Form` 初始值来自新结构；若 `hasSavedCredential` 为真，则用户名/密码输入框显示“已保存，点击更新”按钮，避免再次填充明文。
   - 保存成功后 toast：“配置已保存，请先测试再启用”。
   - 底部保留 `保存`、`测试连接`、`保存并测试` 三个按钮。
3. **测试流程提示**
   - 调用测试接口期间展示进度条与实时日志（若后端提供流式日志则使用 SSE/WebSocket，否则轮询）。
   - 结果面板列出成功、延迟、服务器地址等指标；失败场景显示详细诊断及建议。
   - 测试通过后弹出对话框：“测试通过，是否立即启用？”并说明启用动作影响。
4. **异常感知**
   - `active` 状态转 `degraded`/`error` 时，页面右上角通知提醒，点击跳转到该数据源详情。
   - 诊断抽屉展示最近测试记录、监控指标、日志引用链接。

## 用户旅程
1. **首次接入**
   - 新增数据源 → 保存配置（状态`pending_test`）→ 测试成功（`ready`）→ 选择启用（`active`）。
2. **修改配置**
   - 编辑 → 保存（回到`pending_test`）→ 测试 → 启用。
3. **运行维护**
   - 监控异常 → 通知提醒 → 查看诊断 → 重新测试/暂停。
