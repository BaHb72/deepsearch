# TGW Python 3.13.7 扩展自编译可行性分析

## 现有资源情况
- 当前 SDK 包含经过 SWIG 生成的 `tgw.py` 和多个针对不同 Python 版本的 `_tgw.pyd`、`tgw.dll` 等二进制。
- 未提供 C/C++ 源码、SWIG `.i` 接口文件、VC 工程或编译脚本。
- 依赖的第三方库包括 OpenSSL（`libcrypto-1_1-x64.dll`、`libssl-1_1-x64.dll`）、Boost 等，版本固定在 VC14 toolchain。

## 自行编译的前提条件
1. 获得 TGW 源码或 SWIG 接口定义（至少需要 `server_spi.py` 对应的 `server_spi.i`/`server_spi.h`）。
2. 获取配套的 C/C++ 工程配置（编译器、宏定义、依赖库路径等）。
3. 使用与官方一致的编译链：Windows 平台通常要求 Visual Studio 2015/2017（VC14），并链接到特定版本的 OpenSSL/Boost。
4. 重新运行 SWIG 生成 Python 3.13 兼容的包装代码，再用 `cl` 或 `msbuild` 生成 `_tgw.pyd`。

## 障碍与风险
- 若无法获取源码，只凭现有的 `.pyd/.dll` 无法逆向补齐 `ILogSpi` 等接口。
- 即便拿到源码，也需要准确的依赖版本；官方可能还有私有静态库或后台服务接口，文档缺失会导致编译失败。
- 与厂商协议相关：自行编译可能违反授权条款，需得到书面许可。

## 结论
- 在目前仅持有二进制制品的情况下，无法自行构建 Python 3.13.7 版本的 `_tgw.pyd`。
- 若要自编译，必须向银河证券获取完整源码、SWIG 接口、编译说明以及依赖库版本，并确认授权。
- 建议优先与供应商沟通获取官方适配版本；自编译作为最后手段，需要投入较大工程成本。
