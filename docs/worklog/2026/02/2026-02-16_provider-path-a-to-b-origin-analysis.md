# Provider 双主路径成因追溯（A -> B 方案）

> 日期: 2026-02-16
> 模块: providers, api/server, dask
> 类型: architecture-analysis

---

## 结论先行

当前出现“两条主路径并存”不是偶然，而是一次未完全收口的渐进迁移结果：

1. **A 方案（全局工厂/分散创建）在生命周期管理上行不通**，引发资源泄漏、状态混乱、测试困难。
2. **B 方案（ProviderContainer + Protocol）是为解决 A 方案根因而引入**，但迁移期间保留了兼容入口，导致双轨长期并存。
3. AmazingData 的 Dask 约束进一步放大了“保留兼容层”的惯性，形成 today 的复杂拓扑。

---

## 证据链

### 证据 1：A 方案的失效原因有明确记录

`docs/worklog/2026/01/2026-01-15_provider-architecture-refactor.md` 直接记录了 A 方案问题：

- 资源泄漏（关闭不彻底）
- 全局状态混乱（多处创建实例）
- 测试困难（全局工厂不可替换）
- API 层与具体实现强耦合

同一文档还记录了尝试路径：

- 方案 A：给旧工厂加 `cleanup()`，失败（调用点不可靠）
- 方案 B：`atexit` 自动清理，失败（异步上下文与重启场景不可靠）
- 方案 C：`ProviderContainer + Protocol`，最终采纳

### 证据 2：B 方案落地是一次“增量迁移”而非“一刀切替换”

同文件写明迁移成本与现实约束：

- “现有 26+ API 端点需要逐步迁移”
- “过渡期需要维护兼容层代码”

这解释了为什么在引入容器后，旧入口仍然长期存在。

### 证据 3：AmazingData + Dask 约束迫使出现桥接逻辑

`docs/worklog/2026/01/2026-01-17_amazingdata_dask-proxy-registration.md` 记录：

- 主进程不应直接加载 SDK（会与 Dask Worker 冲突导致 Segfault）
- 需要通过 `register_external()` 把 Dask 代理桥接注册进 `ProviderContainer`

这意味着 B 方案在生产链路中并非“直接替换 A”，而是新增了一层跨进程适配桥。

### 证据 4：提交历史显示“先并存后收口”的轨迹

- `afc3dad`（2026-01-20）：引入 ProviderContainer / Protocol / ProviderFactory
- `193c31b`（2026-02-07）：继续做“统一数据层 + AmazingData 单通道约束”

说明团队方向一直在向 B 收敛，但并未完成旧路径退役。

---

## 为什么今天仍有两条主路径

从代码与文档可归纳为三点：

1. **迁移节奏保守**：先保证可运行，再逐步替换调用方。
2. **运行约束复杂**：Dask、跨进程 Actor、SDK 限制要求桥接层长期存在。
3. **兼容面广**：API 历史入口、旧管理器能力、已有测试依赖尚未全部迁移。

---

## 后续处理建议

1. 先定义“唯一主路径”判定标准（创建、健康检查、关闭、配置来源四项必须唯一）。
2. 以接口批次推进旧入口退役，按模块迁移并保留可回滚窗口。
3. 每下线一条旧路径，同步删除对应兼容分支与测试桩，防止反向回潮。

---

## 关键结论

> A 方案不是“没实现好”，而是其设计范式无法稳定承载异步生命周期与多数据源扩展；B 方案方向正确，但迁移停在“并存态”，当前任务的核心就是完成“并存 -> 收敛”的最后一段路。
